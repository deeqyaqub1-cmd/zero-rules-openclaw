📖 HyperStack Docs

Everything you need to give your AI agent persistent, queryable memory.

WHAT IS HYPERSTACK?

HyperStack gives your AI agent a memory it can actually use.

Instead of stuffing context into every prompt, your agent stores what it learns as structured cards, connects them into a graph, and retrieves exactly what it needs — by keyword, by type, by relationship, or by time.

Think of it as a second brain for your agent. One that remembers decisions, tracks blockers, maps relationships, and can tell you exactly what it knew when it made a choice.

🃏 CARDS — The Basic Unit of Memory

A card is one chunk of knowledge. It could be a decision your agent made, a person on your team, a project it's tracking, or a preference it should always respect.

Every card has:

slug   Unique ID. Store to the same slug = update, not duplicate.
          Example: "decision-use-clerk"

title   Human-readable name.
          Example: "Use Clerk for Auth"

body   The actual content — what the agent needs to know.
          Example: "Chosen over Auth0 for better Next.js DX and lower cost."

cardType   person | project | decision | preference | workflow | event | general

stack   people | projects | decisions | preferences | workflows | general

keywords   Tags for fast exact-match search. Example: ["clerk", "auth", "login"]

links   Connections to other cards — builds the graph.
          Example: [{ slug: "deploy-prod", relation: "blocks" }]

Quick rule: one card = one idea. Keep them small and focused.

🔗 THE GRAPH — Connect Everything

Cards become powerful when you link them. Links have a relation type that tells the agent how two things are connected.

Built-in relation types:

blocks   This card is stopping another from moving forward
depends-on   This card needs another to be complete first
triggers   This card causes another to activate
owns   A person or agent owns this card
decided   A person or agent made this decision
related   General connection — catch-all

Example:

"auth-migration" blocks "deploy-prod"
"deploy-prod" depends-on "auth-migration"
"alice" decided "use-clerk"

Once linked, you can ask: "What blocks deploy?" or "What breaks if auth changes?" — and get instant answers from the graph.

🔍 SEARCH — Find What You Need

HyperStack has two ways to find cards:

Keyword search   Exact match on keywords, slug, or title. Fast. No embeddings needed. Works offline.

Semantic search   Meaning-based search using embeddings. Finds cards even when wording doesn't match exactly. Requires OpenAI API key or local Ollama model.

Start with keyword search — it covers most use cases.

⏱ DECISION REPLAY — Understand Why

Every card is timestamped. HyperStack remembers not just what your agent knows, but when it learned it.

Decision Replay lets you ask: "What did the agent know when it made this decision?"

It shows you:

  • Which connected cards existed at decision time
  • Which cards were added or changed afterwards
  • Whether any post-decision changes could have affected the outcome

This is how you audit an agent's reasoning — not by reading logs, but by replaying its memory state.

🧱 BLOCKERS & IMPACT — Know What's Stuck

Two of the most useful queries in HyperStack:

Blockers   "What is preventing this card from completing?"
      Traverses the graph and surfaces everything blocking a target.

Impact   "What breaks if I change this card?"
      Traverses downstream links to show the blast radius of a change.

Example:

blockers("deploy-prod") → ["auth-migration", "stripe-integration"]
impact("use-clerk") → ["auth-api", "deploy-prod", "billing-v2"]

Use these before making changes. Know the consequences first.

🧠 MEMORY TYPES — Not All Memory Is Equal

HyperStack supports three memory surfaces:

Semantic   Facts that never age. Decisions, people, preferences. Permanent — no decay, no expiry.

Episodic   What happened and when. Event traces, session history. Soft 30-day decay curve. Agent-used cards decay slower.

Working   Short-term scratchpad. Active task context. TTL-based — expires after a set time. Agent use extends TTL.

Tag a card with memoryType when storing it. Query by type to get only what's relevant right now.

🤝 AGENT IDENTITY — Know Who Did What

Each agent registers with a slug at session start. Every card it stores is automatically stamped with its identity.

This means you always know:

  • Which agent stored a card
  • Which agent last updated it
  • Whether the information came from a trusted source

Agents build a trust score over time: (verified cards / total) × 0.7 + (activity) × 0.3. High trust = more weight in conflict resolution.

🌿 BRANCHING — Safe Experimentation

Before trying something risky, fork your workspace. Make changes in the branch. If it works, merge. If not, discard — your main memory is untouched.

fork()   Creates a copy of your workspace to experiment in
diff()   Shows what changed between branch and main
merge()   Applies branch changes back to main
discard()   Deletes the branch, main is unaffected

Think of it as git for agent memory.

⚡ QUICK START

1. Install

npm i hyperstack-core
or: pip install hyperstack-py

2. Store your first card

await hs.store({
  slug: "my-first-decision",
  title: "Use PostgreSQL for storage",
  body: "Chosen for reliability and Neon's serverless pricing.",
  cardType: "decision",
  stack: "decisions",
  keywords: ["postgres", "database", "storage"]
});

3. Search

await hs.search({ query: "database" });

4. Check blockers

await hs.blockers("deploy-prod");

5. Traverse the graph

await hs.graph({ from: "my-first-decision", depth: 2 });
